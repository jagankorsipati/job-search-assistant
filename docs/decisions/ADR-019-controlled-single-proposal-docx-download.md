# ADR-019: Controlled Single Proposal DOCX Download

## Status

Verification note, 2026-09-19: the decision below retains its historical milestone scope. Current implementation includes ADR-019's ephemeral single-proposal download; ordinary wording approval is not target-bound approval, and editing a proposal cannot retarget a replaced source. Local LibreOffice-container rendering evidence is recorded in the [release record](../security/phase-6-verification.md) and [fidelity matrix](../docx-fidelity-matrix.md). No Microsoft Word-fidelity claim is supported.

Accepted implementation design. Local Phase 6E/6F rendering and browser release checks are complete for the current supported DOCX boundary; hosted CI for the resulting commit remains pending until pushed.

## Scope and evidence

ADR-018's whole-paragraph replacement engine is promoted unchanged into the internal Documents module, with an additional result exposing the actual extracted paragraph text. Synthetic fixtures retain the same supported edits, refusals, archive/XML limits, and preservation assertions. No document-processing dependency is added. Local rendered evidence now covers the current supported boundary in a disposable LibreOffice container; structural evidence alone still does not prove layout or Word fidelity.

One saved proposal produces one separate DOCX. There is no batch combination, source overwrite, AI, external fetch, or application submission.

## Target-bound approval

Owner-scoped endpoints under `/api/documents/resume-tailoring-proposals/{id}` are `GET /resolved-review?expectedVersion=...`, `POST /approve-resolved`, and `POST /export`. Approval requires `expectedVersion`, exact `resolvedRevision`, and true `attestedTargetAndExperience`. Export requires expected version and resolved revision as a separate deliberate request. Unsafe operations require CSRF; all responses are no-store.

Resolved review displays actual extracted source text, intended replacement, main-document part/body location, source attribution, evidence versions, and whether a current resolved approval exists. User-supplied original text is used only to locate an exact unique whole-paragraph match; it is never silently relabeled verified experience. Free-form target references are not anchors. Missing, ambiguous, unsupported, or changed targets refuse.

The resolved revision hashes `DOCX_WHOLE_PARAGRAPH_V1`, the existing proposal/source/evidence review token, exact source checksum, body-child index, and paragraph XML digest. The proposal version binds the exact replacement; the review token binds all supporting fact versions. V13 adds nullable `resolved_target_revision` to decision history, constrained to approved decisions and 64 hexadecimal characters. Resolved approval appends a normal approval and assigns its binding before the same transaction commits. No existing decision is retrofitted. Legacy NULL bindings never authorize export.

Resolution does not alter the proposal. If wording, original text, target reference or evidence needs editing, the existing update path increments the proposal version and returns it to draft. The owner must review and attest again. Historical approval attribution remains intact.

## Authorization point and concurrency

Operations derive ownership through `CurrentActorProvider`; ADMIN has no bypass. Short transactions lock the proposal and links, source row, and confirmed facts, then check versions and eligibility. A bounded source snapshot is read under those locks and hashed against source metadata. Resolution and document generation execute outside database locks.

Before approving a resolved target, the service reacquires locks and checks the captured review token against current proposal/source/fact state, then persists the decision and binding atomically. Before returning generated bytes, it reacquires locks and requires current lifecycle `APPROVED`, current eligibility, the exact resolved revision, and the same latest decision identity captured before generation. Proposal edits, resume replacement, changed facts (even still CONFIRMED), rejection, or a different decision refuse and discard the generated result.

**The final successful transaction immediately before returning the completed resource is the export authorization point.** Later changes cannot retract already authorized bytes. No database lock is held during network streaming. Tests pause generation and commit proposal/source/fact/rejection changes while it is paused, demonstrating that generation holds no such locks and that changed state prevents release.

## Output, bounds and privacy

The complete output passes the Phase 6D engine's package checks before response construction. The response uses a byte resource, fixed filename `tailored-resume.docx`, DOCX media type, explicit length, `nosniff`, and no-store. The resource wrapper and redacted request/review DTO string representations avoid emitting content or review tokens through framework debug descriptions. Errors expose fixed codes, never paths or document text.

Generation concurrency is capped at two requests per process, with immediate busy refusal. Inherited bounds are 5 MiB input/output archives, 512 entries, 8 MiB per expanded part, 25 MiB total expansion, 2 MiB XML parts, depth 128, and 100:1 entry ratio. Temporary ZIP snapshots are deleted in `finally`, streams close on all paths, and no named archive entry is extracted. External resources/macros are never activated.

This milestone uses an ephemeral download response, not a persisted export artifact. It supersedes ADR-018's proposed persistent export-record/file publication step for this initial milestone. There is no retained generated file, storage key, or retrieval endpoint; approval history retains the exact binding. A future stored-export design must separately define audit metadata, retention, staleness and retrieval authorization.

The frontend keeps private data and tokens in memory, requires an initially unchecked target attestation, and invalidates review on edits/selection/review changes. Download is separate from approval, uses the shared CSRF/session client, creates an object URL only after a successful DOCX response, and revokes it after requesting the browser download. It reports response received/download requested, not that a file was saved. Failures clear the review and never retry approval automatically.
