# Phase 4 Verification Matrix

Phase 4 covers owner-scoped job capture, immutable job-description snapshots, application tracking, explicit status history, frontend workspaces, duplicate warnings, and browser privacy.

| Area | Evidence |
| --- | --- |
| Schema and ownership foundation | Flyway migrations define owner-scoped `captured_job`, `job_description_snapshot`, `job_application`, and `application_status_history` tables with owner-aware parent/child integrity and restrictive deletion posture. |
| Job APIs | Backend tests cover authenticated creation, URL-reference normalization without fetching, owner-derived access, snapshot sequencing, latest-snapshot duplicate rejection, optimistic conflicts, archive/restore, CSRF, and safe missing/non-owned responses. |
| Application APIs | Backend tests cover owner-scoped draft creation, one application per owner/job, narrow job validation, notes/next-action updates, explicit transition matrix, append-only history, terminal behavior, optimistic conflicts, archive/restore, CSRF, and safe cross-owner denial. |
| Frontend workspaces | Component tests cover capture/edit/archive/restore, immutable snapshots, duplicate warnings, search/source/employment filters, application status/text/due filters, explicit status transitions, conflict recovery, and no owner identifiers in browser-submitted payloads. |
| Browser verification | `frontend/e2e/job-application-security.spec.ts` exercises anonymous denial, member and admin isolation, job and application UI lifecycles, URL-reference no-fetch behavior, duplicate warnings, immutable snapshots, status history, CSRF rejection, optimistic conflicts, safe cross-owner API shapes, and browser storage/cookie/URL privacy. |
| CI coverage | The browser CI job runs `scripts/run-browser-e2e.ps1`, which executes the full Playwright suite. Screenshots, traces, videos, browser profiles, raw error contexts, and HTML reports remain disabled or discarded; CI uploads only sanitized diagnostics on failure. |
| Test independence | Every spec (`identity-security`, `profile-security`, `job-application-security`) authenticates its own uniquely named runtime accounts (a `Date.now()`-and-random-suffixed login per run), passes individually, and passes regardless of file/execution order. No spec depends on state created by another spec's account. The shared, fixed administrator account is logged in once per spec (session reused across a spec's own steps) rather than repeatedly, and the profile-save helper detects and reuses an already-existing administrator profile instead of assuming first-time creation, so the suite stays deterministic even when re-run repeatedly against one live environment. |
| Login/rate-limit posture | Login/profile-save helpers wait for the exact `POST /api/auth/login` and `POST`/`PUT /api/profile` responses and assert on their HTTP status before checking rendered UI state, rather than masking a failed write behind a bounded `/api/auth/me` poll. `scripts/run-browser-e2e.ps1` raises `LOGIN_RATE_LIMIT_LOGIN_ATTEMPTS`/`LOGIN_RATE_LIMIT_SOURCE_ATTEMPTS` as process-scoped environment variables for the disposable E2E backend only; `application.properties` keeps the shipped production defaults (5 login attempts / 20 source attempts per 15-minute window) unchanged, proven by `LoginRateLimiterProductionDefaultsTests`. |

Deferred scope remains unchanged: scraping, URL fetching, AI analysis, reminders, deletion/recovery, delegated access, role changes, additional administrators, malware scanning, job-board adapters, notifications, and application submission.
